# TypeScript Interview Questions & Answers


## 1. `interface` vs `type`

**Q: What's the difference between `interface` and `type` in TypeScript?**

**A:**
**Declaration merging:** Interfaces with the same name automatically merge together. Type aliases throw an error if redeclared.
- **Flexibility:** `type` can represent unions, intersections, tuples, and primitive aliases. `interface` is meant for object/class shapes only.
- **Extending:** Interfaces use `extends`. Type aliases use intersections (`&`).
- **Classes:** `interface` reads naturally with `implements` for class contracts.

**Example — Declaration merging (interface):**
```typescript
interface User {
  name: string;
}

interface User {
  age: number;
}

// User is now automatically merged into:
// { name: string; age: number }
```

**Example — Same thing with `type` (fails):**
```typescript
type User = {
  name: string;
};

type User = {   // ❌ Error: Duplicate identifier 'User'
  age: number;
};
```

**When to use which:**
- Use `interface` for public API shapes, class contracts, anything meant to be extended.
- Use `type` for unions, intersections, and utility type compositions.

## 2. Union Types

**Q: What is a union type and why is it useful?**

**A:** A union type restricts a variable to one of several specific types, using the `|` (pipe) symbol.

```typescript
type RequestStatus = "loading" | "success" | "error";

let status: RequestStatus = "loading"; // ✅ valid
status = "done"; // ❌ Error: not assignable to type 'RequestStatus'
```

This gives compile-time safety for things like API call states, form validation states, or button variants — something `interface` cannot do, since interfaces only describe object shapes, not a fixed set of allowed values.

## 3. Generics

**Q: What are generics and why do we need them?**

**A:** Generics let a function, class, or type work across multiple types while preserving type safety — instead of using `any` (which loses safety) or writing a separate function per type (which is repetitive).

**Basic example:**
```typescript
function identity<T>(value: T): T {
  return value;
}

identity(5);       // T is inferred as number
identity("hello"); // T is inferred as string
```

**Real-world example — fetching different entity types:**
```typescript
interface UserInfo {
  id: string;
  name: string;
}

interface AdminInfo {
  id: string;
  name: string;
  permissions: string[];
}

interface EditorInfo {
  id: string;
  name: string;
  assignedArticles: string[];
}

interface ViewerInfo {
  id: string;
  name: string;
  subscriptionTier: string;
}

// One generic function, return type is also generic (T)
async function fetchEntity<T>(id: string): Promise<T> {
  const response = await fetch(`/api/entities/${id}`);
  return response.json() as T;
}

// Usage — T is locked to a specific type at each call site
const admin = await fetchEntity<AdminInfo>("123");
console.log(admin.permissions); // ✅ works

const viewer = await fetchEntity<ViewerInfo>("456");
console.log(viewer.subscriptionTier); // ✅ works
console.log(viewer.permissions);      // ❌ Error: ViewerInfo has no 'permissions' field
```

**Key rule:** If the function should return exactly the type passed in, the return type must also be the generic `T` — not a hard-coded type. Otherwise TypeScript will throw an error when the hard-coded return shape doesn't match what the caller expects.

**Constraining a generic (shared field):**
```typescript
interface HasId {
  id: string;
}

function logEntityId<T extends HasId>(entity: T): void {
  console.log(entity.id); // ✅ safe — TypeScript knows T has an id
}
```
`T extends HasId` means "T can be anything, as long as it has at least an `id` field."

## 4. Utility Types — `Partial`, `Pick`, `Omit`

**Q: What do `Partial`, `Pick`, and `Omit` do?**

**A:**

**`Partial<T>`** — makes every field optional. Useful for update functions.
```typescript
type PartialUser = Partial<UserInfo>;
// { id?: string; name?: string }
```

**`Pick<T, Keys>`** — creates a smaller type with only the selected fields.
```typescript
type NameOnly = Pick<UserInfo, "name">;
// { name: string }
```

**`Omit<T, Keys>`** — creates a type with everything *except* the excluded fields. Useful for create-user scenarios where the ID is generated by the backend.
```typescript
interface UserInfo {
  id: string;
  name: string;
  username: string;
  password: string;
}

type NewUser = Omit<UserInfo, "id">;
// { name: string; username: string; password: string }
```

## 5. Enums vs Union Types

**Q: When would you use an `enum` vs a union type?**

**A:**
```typescript
// Enum — generates real runtime code
enum UserRole {
  Admin,
  Editor,
  Viewer,
}
UserRole.Admin; // accessible at runtime

// Union type — compile-time only, no runtime footprint
type UserRole = "admin" | "editor" | "viewer";
```
Most modern TypeScript codebases prefer **union types** over enums — enums add runtime overhead and can behave unexpectedly when compiled, while union types are lighter and equally type-safe.

## 6. Type Narrowing

**Q: What is type narrowing?**

**A:** TypeScript narrows a broader type to a more specific one based on runtime checks in your code.

```typescript
function printValue(value: string | number) {
  if (typeof value === "string") {
    // Inside this block, TypeScript knows value is a string
    console.log(value.toUpperCase()); // ✅ safe
  } else {
    // Here, TypeScript knows value is a number
    console.log(value.toFixed(2)); // ✅ safe
  }
}
```
Outside the `if` block, the type widens back to `string | number`.

## 7. `unknown` vs `any`

**Q: What's the difference between `unknown` and `any`?**

**A:**
- **`any`** disables type checking completely — you can call any method or access any property, and TypeScript won't complain, even if it's wrong.
- **`unknown`** keeps type checking active — you must narrow the type (e.g., with `typeof`) before you're allowed to use it.

```typescript
let valueAny: any = fetchData();
valueAny.toUpperCase(); // No error, even if this crashes at runtime

let valueUnknown: unknown = fetchData();
valueUnknown.toUpperCase(); // ❌ Error: must narrow first

if (typeof valueUnknown === "string") {
  valueUnknown.toUpperCase(); // ✅ safe, narrowed to string
}
```
**Analogy:** A mystery box typed `any` — TypeScript lets you do anything with it, no questions asked. A mystery box typed `unknown` — TypeScript won't let you touch anything inside until you prove what it actually is.

`unknown` is the safer choice for things like API responses where the shape isn't known yet.

## 8. Optional Chaining & Nullish Coalescing

**Q: What are `?.` and `??` used for?**

**A:**

**Optional chaining (`?.`)** — safely accesses nested properties that might not exist, returning `undefined` instead of throwing.
```typescript
const city = user?.address?.city;
```

**Nullish coalescing (`??`)** — provides a fallback only when the left side is `null` or `undefined`.
```typescript
const nickname = user.nickname ?? "Guest";
```

**Why not just use `||`?**
```typescript
const count = 0;
count || 10;  // 10  — WRONG, 0 is falsy but is a valid value
count ?? 10;  // 0   — CORRECT, 0 is not null/undefined, so it's kept
```
`??` only replaces `null`/`undefined`, so legitimate values like `0` or `""` pass through untouched.

## 9. Type Assertions (Type Casting)

**Q: What is a type assertion and when would you use one?**

**A:** A type assertion tells TypeScript "trust me, I know the actual type here," when TypeScript can't infer it correctly on its own. It doesn't convert the value — it only affects how the type checker treats it.

```typescript
const input = document.getElementById("my-input") as HTMLInputElement;
input.value; // ✅ works — without the assertion, TypeScript only knows it's HTMLElement | null

let value: unknown = 42;
const num = value as number; // simple example
```
**Caution:** If the assertion is wrong (e.g., the element is actually a `<div>`), TypeScript won't catch it — you'll only find out at runtime.

## 10. `readonly` vs `const`

**Q: What's the difference between `readonly` and `const`?**

**A:**
- **`const`** prevents reassigning the *variable binding* — but object properties can still be mutated.
- **`readonly`** prevents reassigning a *specific property* on an object/interface.

```typescript
const user = { name: "John" };
user = { name: "Jane" }; // ❌ Error — can't reassign the variable
user.name = "Jane";      // ✅ Allowed — const doesn't protect properties

interface UserInfo {
  readonly name: string;
}

const user2: UserInfo = { name: "John" };
user2.name = "Jane"; // ❌ Error — readonly protects this specific property
```

## 11. Mapped Types

**Q: What is a mapped type?**

**A:** A mapped type builds a new type by applying the same transformation to every property of an existing type, instead of writing the transformation by hand for each field.

```typescript
interface UserInfo {
  id: string;
  name: string;
}

// Custom mapped type — makes every field readonly
type ReadonlyUser = {
  readonly [K in keyof UserInfo]: UserInfo[K];
};
// Equivalent to: { readonly id: string; readonly name: string }
```

**Analogy:** Like laminating a library card template — instead of laminating "title" and "author" separately, you apply one rule that automatically covers every field on the card, even future fields.

This is exactly how built-in utility types like `Readonly<T>`, `Partial<T>`, and `Pick<T>` are implemented internally.
